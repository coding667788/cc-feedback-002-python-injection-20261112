我们需要从零开发一个离线 Python 注入漏洞分析引擎，审计采用 FastAPI 风格路由的 Python 项目。它必须能回答：某个外部输入经过哪些跨模块调用、字段读写和分支，到达了哪一个危险参数；修改一个公共函数后，哪些旧结论需要失效。工作区没有已有扫描器，请交付可运行实现、结构化发现报告、可重复测试和设计说明。

使用 Windows 原生 Python 3.12，可使用标准库 ast、sqlite3 等基础设施。不得把 Semgrep、CodeQL、商业扫描服务或大模型接口作为分析内核。全程只解析源码，不导入、执行被扫描项目，不运行漏洞样例中的 SQL 或系统命令，不连接真实目标。样例工程和测试数据也属于本次从零开发的交付内容，无待提供的外部附件。

一、明确支持的分析范围
1. 支持包内绝对/相对导入、导入别名、顶层函数、async/await、直接函数调用、位置/关键字参数、默认参数、返回值及固定属性名的简单对象字段；支持常量键字典、常量下标列表、容器别名和字段写入。对能静态定位到唯一类定义的构造器和实例方法保留字段传播，不要求处理动态继承或描述符。框架装饰器只作静态入口识别，不要求实际安装或启动 FastAPI。
2. 支持 if/elif/else、for/while、break/continue、try/except/else/finally 的控制流。循环和递归调用必须收敛，不能仅把循环展开一次，也不能依赖无限递归。路径条件至少能区分同一变量的 None 判断、布尔分支和互斥的字符串常量相等条件。
3. 不要求处理任意 Python 的动态语义。eval/exec、运行时生成的导入名、任意反射、猴子补丁、未知动态调用目标可以报告 unsupported 或 unknown；但必须给出位置、原因和影响范围。已经承诺支持的语法不能全部降级为 unknown，也不能把无法分析写成“没有漏洞”。

二、污点与危险点语义
4. 路由参数中的外部标量、request.query_params.get、request.path_params 的索引，以及 await request.json() 返回对象中被读取的字段，均属于外部来源。函数内局部常量不是外部来源。字典一个字段被污染，不应无条件把其全部无关字段一起污染。
5. SQL 危险点包括 sqlite3 连接及游标的 execute/executemany 查询字符串参数，需要追踪 sqlite3.connect 和 cursor 的已知返回对象，不能把任意同名方法都当作 SQL。将外部值插入查询字符串应报警；固定查询模板加独立绑定参数不因此报警；查询字符串本身受污染时，即使同时传入绑定参数也不能视为安全。
6. 命令危险点包括 os.system 和 subprocess.run/Popen/call 在 shell=True 时的命令参数。shell=False、固定原生可执行文件名、外部值仅位于普通 argv 参数中的情况，不应误报为 shell 字符串注入。动态可执行文件、.bat/.cmd 和无法确定的 shell 选项要单独标明未决风险，不能套用上述安全结论。
7. 净化结论必须来自实际数据变换及其控制流位置，不能因为函数名叫 escape、safe 或 sanitize 就相信它。至少识别“成功 int 转换后再规范化为十进制字符串”的有限净化规则；转换异常分支中继续使用原始字符串仍然受污染。html.escape 不能被当成 SQL 或命令净化。只在某个分支成立的净化，不能传播到未经净化的其他分支。

三、分析引擎的正确性要求
8. 建立跨模块调用与依赖关系，实施调用上下文和字段敏感的数据流分析。同一个包装函数被可信常量调用及外部输入调用时，不能把两种调用的结论混成一条不可能的证据路径。对深度至少为二的调用点上下文保留区分；递归需要说明采用的抽象、合并和收敛策略。
9. 生成的 source-to-sink 证据必须包含文件、行列、函数、字段/参数位置、调用/返回边以及必要的分支条件。不得拼接来自互斥分支或不同调用实例的边来伪造一条路径。超出已支持条件域的路径可以标记“可行性未知”，但不能伪称已证明可行。
10. 为每项发现生成确定性的指纹和排序。仅插入空行、调整无关格式时，发现的逻辑身份不应改变，行列位置则应正确更新。报告中同时给出分析覆盖、未知调用和资源耗尽诊断，不能只输出漏洞数量。
11. 实现持久化增量缓存。缓存键必须覆盖源文件内容、解析/规则版本、函数摘要和所依赖的调用目标；修改、删除、重命名公共模块或改变导入别名后，要使受影响调用者失效，不能保留已经不存在的旧发现。未受影响模块应有可核查的缓存复用记录。对同一版本项目，全量分析和增量分析得到的发现、证据及未决诊断在去掉耗时等运行统计后必须一致。
12. 在缓存写入中途被结束进程后，用原缓存重启也必须恢复为与干净全量分析一致的结果。旧缓存格式或规则版本不兼容时，应明确迁移或安全重建，不能静默接受。分析超时、语法错误和内存预算耗尽须产生明确的不完整状态，不能以“零漏洞”成功退出。

四、必须提交的可核验用例
至少构造并自动验证以下场景：跨三层模块的真实传播；同一函数两个不同可信度调用；同一对象两个字段只有一个受污染；容器别名修改；互斥分支形成的伪路径；int 转换成功与异常分支；try/finally 中的危险调用；固定 SQL 参数绑定与污染查询模板；shell=True 与固定原生程序 shell=False 的差别；循环携带污点；递归调用收敛；公共函数修改后增量结论撤销；模块删除/重命名；缓存事务提交前中断。

正反例必须成对，断言具体来源、危险参数和证据边，不能只断言进程退出码或报告文件存在。测试中的期望清单只能由测试程序读取，分析引擎不得读取 expect 注释、文件名约定或答案清单来生成发现。还需提供语义保持变换测试，例如插入空行、改局部变量名和增加无关模块，检查结论稳定性。

交付导入式 Python API、离线批量分析入口、稳定的 JSON 报告结构、样例工程生成器、自动化测试和 Windows 运行说明。用不少于 50 个模块、500 个函数的合成项目记录冷启动与增量分析耗时、峰值内存、缓存命中及失效范围；性能数字必须实测，超限要如实暴露。说明抽象域、CFG/调用图构造、上下文合并、未知语义边界，以及为什么全量和增量能保持同一结论。未实现或未验证部分应明确列出。
